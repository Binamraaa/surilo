# Hum to Notes: notes for Claude Code

A browser app: hum a melody, then see the notes as blocks, on a guitar fretboard, a piano and a staff, with a key guess and chord suggestions. It's a public GitHub portfolio project. It's meant for quick experimenting, not studio-grade transcription.

## Stack and constraints
- Vanilla JS ES modules, no framework and **no build step**. `index.html` loads `src/app.js` directly. Keep it that way so GitHub Pages serves the repo root as-is.
- No runtime dependencies. `esbuild` is a dev-only dependency, used only by `scripts/build-single.mjs` (an optional single-file bundle in `dist/`, which is gitignored).
- The mic needs `https://` or `localhost`.

## Commands
- `npm test`: Node's built-in test runner on `test/*.test.mjs`. Run it after any change to `src/core`.
- `node scripts/sweep.mjs [steady|sloppy|chromatic] [--misses]`: accuracy sweep over 522 synthetic hums. Caches pitch frames in `.cache/` (gitignored); delete it after changing `pitch.js` or `demo.js`.
- `python -m http.server 8000` (or `npx serve`), then open http://localhost:8000
- `node scripts/real-hums.mjs <folder> [--misses]`: grades the current code on real test hums (WAVs saved from test mode). The user's set is in `G:/My Drive/Hum to Notes tests` (Google Drive for desktop); `$HUM_TESTS` or `testdata/hums/` (gitignored) also work. Run it before and after accuracy changes, alongside the sweep.
- `npm run build`: bundles `dist/hum-to-notes.html` and `dist/embed.html` (needs `npm i`)

## Architecture
- `src/core/`: **pure logic, with no DOM and no Web Audio**. It must keep running in Node. This module will later feed hummed ideas as MIDI into a separate Reaper-based "AI producer" project, so keep it clean and dependency-free.
  - `pitch.js`: YIN detector (input is downsampled ×2 when the sample rate is above 30 kHz), RMS gate, adaptive gate. The live view uses plain YIN frame by frame (`analyseFrame`). `analyseBuffer` (whole recordings, run again when you press Stop) is pYIN-style: `yinCandidates` gives every dip a chance from a Beta prior over thresholds, an octave-up check moves the chance to the dip at twice the lag when that one is far deeper (weak fundamental, "mmm" on a phone mic), candidates far from the middle of the hum lose out to a rival an octave nearer, and `trackPitch` (Viterbi) picks a smooth path with a jump cost and a "no pitch" option, so brief octave flips and octave-down shadows on fading notes disappear. `track: false` gives plain YIN
  - `notes.js`: `framesToNotes`. Median smoothing, then segmentation: a pitch change has to hold for `changeMs`, a loudness dip followed by a rise re-articulates repeated notes, the attack (first 25%) is ignored when picking a note's pitch, and the tuning offset is estimated from note centres (circular mean)
  - `theory.js`: Krumhansl–Kessler key profiles plus an out-of-scale penalty and a small major-key prior; chord suggestions per phrase (groups of 4 notes or split on pauses, with a cadence bonus on the last note); `chordsWithNote` (the chords that contain one note, used live and for the playing or selected note); `voiceChord` (plays chords around E3–D♯4 so small speakers can reproduce them); Viterbi guitar fingering; staff spelling
  - `intent.js`: `transcribe` = `framesToNotes` + `intendNotes`. Follows the singer's drift (circular mean over ±6 neighbouring notes, unwrapped note by note, leaving the note itself out). Notes more than 20¢ from a semitone get two candidates, and a Viterbi pass scores pitch distance, a mild out-of-key penalty and melodic step size. Notes it moves get `adjusted: true` + `nearest`. `trust` (learnt in app.js from Keep/Use answers, kept in localStorage) scales the key and step terms
  - `modes.js`: the seven modes around a home note (Ionian, Mixolydian, Lydian, Dorian, Aeolian, harmonic minor, Phrygian) and `modeChords`. **Spelling goes by scale degree** (`spell()`, `prefersFlats()`): C♯ in D harmonic minor, D♭ in C Phrygian. harmony.js uses `spell` for chord names. Nothing rewrites the melody any more
  - `harmony.js`: `harmonise(notes, {home, slots, journey, variations})` picks chords for a melody in a mood without ever touching the notes. `CHORD_TYPES` is the compatibility table (chord tones, tensions, colour tensions for colourful moods, avoid notes, in semitones above the root); `noteRole`/`supports` read it. Slots come from `phraseSlots` (theory.js); each mood's rate joins two slots (Dreamy) or halves one (Jazzy). In each span, the first note, the longest, long notes and the melody's last note are "strong" and must be supported by the chord, or the chord is `borrowed` (from `chordsWithNote`; `clash` if even that doesn't fit). A k-best Viterbi (state = chord + how long it's been held) scores fit, palette preference, the mood's moves, shared tones and its cadence, and returns 2–3 variations that differ by at least two chords. Each chord carries a plain-words `why`. Deterministic. **Journeys** (one mood id per slot): where the mood changes, a chord in both palettes gets a pivot bonus; if none fits, the old side is offered the V7 of a chord the new mood can start on (a turnaround). Ending bonuses only count inside the last mood's stretch. `lift: true` lets the last chord be the major home chord (the Picardy lift)
  - `moods.js`: the nine moods as data (palette as Roman numerals, moves, cadence, avoided endings, chord-change rate, colour), with separate recipes for a major and a minor home. `JOURNEYS` are the presets (Steady, Bright → Dark, Dark → Hopeful with the lift, …), and `journeyFor(preset, slots, {mood, at})` turns one into a mood per slot, changing about halfway and preferring a phrase boundary. Numerals are counted from the home note: `V7/ii` is a secondary dominant, `♭VII/1` a slash chord over scale degree 1
  - `edit.js`: pure note-editing operations (transpose, reshape, add, delete, split, merge) plus an undo stack. Deleting a note hands its time to the notes touching it (and rejoins them if they're the same note), because a wrong note is usually a glitch inside a held note. Every operation returns a new array, and notes carry a stable `id` so the selection follows a note when the array is re-sorted
  - `rhythm.js`: tempo and the beat grid. A "beat" is one grid unit and one metronome click: a quarter in 4/4 and 3/4, an eighth in 6/8 (where the BPM counts dotted quarters, so `secondsPerBeat` = 60/bpm/3). `accentLevel` (2 = beat 1, 1 = beat 4 in 6/8), `tapTempo` (median of the last 8 taps, reset after a 2 s pause, clamped 40–240)
  - `wav.js`: 16-bit PCM WAV writer and a reader for PCM/float WAVs. A test hum's answer key is JSON in a custom `json` chunk after the audio (one file per hum: Android's share sheet won't share .json files)
  - `midi.js`: SMF format 1 writer (conductor track, melody track, chords track)
  - `demo.js`: synthetic hum generator (vibrato, scoops, detune, noise, plus optional `sloppyCents` per-note misses and `driftCents`). Used by the sample dropdown, the tests and the sweep
- `src/audio/metronome.js`: lookahead click scheduler (a 25 ms timer books clicks 100 ms ahead on `ctx.currentTime`; never time clicks with `setTimeout`). Click times are `anchor + n × spb` from the last tempo change, so they never drift. A late wake-up skips missed clicks instead of bursting. Count-in bars have negative bar numbers; `barOneAt` and `clickTimes` are exposed for recording. Clock, timers and the click sound are injectable, so `test/rhythm.test.mjs` runs it on a fake clock. It shares `getCtx()` from `synth.js` and holds a screen wake lock while running
- `src/ui/metronome-panel.js`: the Metronome card (collapsed by default on phones) and the floating pill shown while it runs and its dots are off screen. Settings are saved in localStorage under `hum-to-notes.metronome`
- `src/audio/`: `mic.js` (ScriptProcessor, hop 1024, rolling loudness gate between the room noise and the loud end of the last ~3 s, so it works with quiet laptop mics), `synth.js` (playback)
- `src/ui/views.js`: functions that return SVG/HTML strings, plus `drawTrace` (canvas). They hold no state.
- `src/ui/roll.js`: the editable piano roll. **Mobile is the priority, because this is heading towards an app.** Rows are 30 px and resize zones 18 px on `(pointer: coarse)`. A touch that starts on a note calls `preventDefault` on `touchstart` (a non-passive listener, in the capture phase), so the page doesn't scroll. **Never re-render the roll during pointerdown**: it replaces the touched element, and mobile browsers then lose the touch and scroll the page. Selection is applied on pointerup. On phones the toolbar docks to the bottom of the screen (`.tools.docked`) while a note is selected. Zoom is `roll.zoom(factor)`. Pointer drags lock to one axis (vertical = pitch, horizontal = time or edge resize), and only the dragged bar is redrawn until you let go. It sends `onEdit({type, ...})` to `applyEdit` in app.js
- **Layout:** four sections (`#view-hum`, `#view-notes`, `#view-chords`, `#view-play`) switched by `showView()` in app.js. The tab bar (`#tabs`) is fixed at the bottom on phones (≤ 720 px) and sits in the top bar otherwise. A hidden section has no width, so `showView` redraws the trace and the roll when theirs opens. The playback bar (`#player`) floats above the tabs, and `setPlaying()` turns the playing button into Stop. `setStatus()` shows a toast that fades (warnings, and messages while listening, stay until tapped). While a note is selected on a phone, the docked editor toolbar hides the tabs and the playback bar. After the user records, uploads or picks a sample, the app opens Notes; the sample loaded at start-up stays quiet. The top-bar chip (`#context`) shows the key and mood and opens Chords.
- **Moods:** a mood only ever changes chords, never notes (tests check this for every mood and journey). `state.moodId` (null = Bright in a major key, Dark in minor), `state.homeKey` (null = the guessed key), `state.journeyId` (a preset from `JOURNEYS`, or `'custom'`) and `state.strip` (one mood per slot once the user edits the mood strip) feed `derive()`, which calls `harmonise` once for the active progression. `state.versions` holds the "Try another version" index per mood (or `'journey'`). The mood cards each call `harmonise` in `renderMoods`, which isn't run during live recording. The mood strip sits under the note blocks: tap a part to pick its mood, press and hold to copy its mood to the end. Playback, the MIDI chord track and the keyboard highlight all use `state.progression`.
- **Editing model:** `state.detected` is the single source of truth (detected first, then edited); `state.original` holds the notes as detected, for Reset. `derive()` feeds everything else from `state.detected`, including playback and the MIDI file.
- **Test mode** (`src/ui/test-mode.js`): `?test=1` turns it on (remembered in localStorage; `?test=0` turns it off). **Save as test** writes the recording at its own sample rate plus `{format: 'hum-to-notes-test', version, song, source, mic, device, tempo, detected, corrected, ...}`, shared via the share sheet on phones or downloaded elsewhere. `scripts/score.mjs` `compareNotes(ref, got)` matches notes by time overlap and labels each answer-key note: correct, semitone, octave, wrong, split, merged or missing, plus extra found notes. Real recordings never go in the repo: the repo is public and they're the user's voice.
- `src/app.js`: a single `state` object; `derive()` recomputes everything that depends on the notes, and the `render*()` functions draw it.

## Conventions
- Pitch is a float MIDI number throughout (69 = A4, middle C = C4 = 60). Notes are `{midi, pitch, cents, start, end}`, with times in seconds.
- All colours come from CSS custom properties in `styles.css`, in light and dark sets. The light set is bright and cool; the dark set is the original. The top-bar button cycles Auto → Light → Dark (`data-theme` on `<html>`, saved as `hum-to-notes.theme`; a one-line script in `<head>` applies it before first paint). Canvas code reads colours when it draws, so redraw it after a theme change. Use `style="fill:var(--x)"` in SVG, never hard-coded colours.
- Copy is written for beginners: plain words, no jargon without explanation.

## Accuracy baseline
`scripts/sweep.mjs`, as of 2026-10-15 (with pitch tracking). "Any key" counts a hum as right if every note is off by the same semitone: a singer 55¢ flat throughout could have meant either key.
- steady (270 hums): 100% exact, with plain rounding and with intent.
- sloppy (192): plain rounding 65.6% exact / 70.8% any key / 93.7% notes. With intent: 81.8% / 90.6% / 97.9%. Most of the gain comes from following drift. Only about 2 in 3 key-based adjustments are right (19 of 29), which is why they're marked and one tap undoes them.
- chromatic (60): 100% with both.
- The synthetic singers never make octave errors, so they can't measure the pitch tracking: check it on real hums (`real-hums.mjs`). On the first 3 real hums it removed all 9 octave errors (8 of them left in the answer keys by mistake).
Re-run before and after changing segmentation or intent parameters. Tune on some seeds and check on others, because the synthetic singers are only a stand-in for real voices.
